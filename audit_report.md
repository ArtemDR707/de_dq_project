# Отчёт по аудиту и исправлению качества данных

**Дисциплина:** Проверка и исправление качества данных (Data Quality)  
**Исполнитель:** Рожков Артём Денисович  
**СУБД:** PostgreSQL 16, база `dataquality`  
**Источник:** [practicum-de/de-dq-project](https://github.com/practicum-de/de-dq-project)  
**Файлы решения:** `student_fix.sql`, `audit_counts.sql`

## 1. Объект и методика аудита

Я провёл аудит четырёх таблиц исходного учебного набора (seed=42):

| Таблица | Строк в исходной выгрузке | Смысл |
|---|---:|---|
| `customers` | 350 | Клиенты |
| `products` | 90 | Номенклатура товаров |
| `promotions` | 25 | Промоакции |
| `orders` | 1 800 | Заказы |

Проверял **полноту** (NULL/пустые строки), **корректность** (форматы и диапазоны), **согласованность** (даты/стоимости), **ссылочную целостность** (JOIN/NOT EXISTS), **уникальность** (GROUP BY/HAVING) и **временную полноту** (помесячные агрегаты). Код `audit_counts.sql` воспроизводимо считает **точное число затронутых исходных строк** по каждому коду дефекта; `student_fix.sql` до любых изменений сохраняет исходные данные в `dq_original_*`. Количества ниже получаются из этих снимков, поэтому повторный запуск не меняет исходную базу для подсчёта.

**Принцип исправления:** сначала восстановить по достоверным связанным данным; затем явно обозначить неизвестное, не придумывая значения; если факт непригоден для аналитического слоя — вынести его в карантин, сохранив оригинал. Нельзя присваивать покупателю чужой телефон, создавать несуществующие заказы или менять реальные даты заказов ради прохождения теста.

## 2. Выявленные дефекты и способы исправления

Столбец «Затронуто» показывает число записей **до исправления**, а не число SQL-операций. Некоторые группы пересекаются, поэтому складывать показатели нельзя.

| № | Таблица / поле | Затронуто, строк | Диагностика | Решение и обоснование |
|---|---|---:|---|---|
| 1 | `orders.customer_id` — пробелы | **{{01_orders_customer_id_with_spaces}}** | `customer_id <> BTRIM(customer_id)` | Удалить пробелы. Известно исходное значение, поэтому восстанавливается без потерь. Пример: заказ №4, `' 98 '` → `98`. |
| 2 | `orders.customer_id` — префикс `CUST_` | **{{02_orders_customer_id_prefixed}}** | `BTRIM(customer_id) ~ '^CUST_[0-9]+$'` | Извлечь цифровой ID из подтверждённого шаблона. Пример: заказ №1153, `CUST_46` → `46`. |
| 3 | `orders.customer_id` — пустой, неразрешимый или отсутствующий в справочнике ID | **{{03_orders_customer_id_unrecoverable}}** | Нормализация + `NOT EXISTS (SELECT 1 FROM customers ...)` | Выставить `NULL`, сохранить заказ. Нельзя назначать случайного клиента. После очистки изменить тип на `INTEGER`, добавить FK. |
| 4 | `orders.product_id` — несоответствующие ссылки | **{{04_orders_product_id_orphan}}** | `NOT EXISTS` в `products` | Если сумма уже известна, сохранить заказ и сумму, а неизвестный товар обозначить `NULL`; не создавать фиктивную карточку товара. Пример: заказ №15, продукт `137` при диапазоне справочника 1–90. |
| 5 | `orders.promo_id` — несоответствующие ссылки | **{{05_orders_promo_id_orphan}}** | `promo_id IS NOT NULL AND NOT EXISTS` в `promotions` | Перевести некорректную необязательную ссылку в `NULL`, не выдумывая акцию. Пример: заказ №4, акция `28` при 25 существующих. |
| 6 | `customers.phone` — отсутствующий номер | **{{06_customers_phone_missing}}** | `phone IS NULL OR BTRIM(phone) = ''` | Невосстановимый телефон хранить с явным маркером `NOT_PROVIDED`, статусом `phone_data_status='missing_in_source'`; во view `dq_usable_customer_contacts` такие значения снова представлены как `NULL`. Реальных номеров я не фабрикую. |
| 7 | `customers.birth_date` — дата рождения в будущем | **{{07_customers_birth_future}}** | `birth_date > CURRENT_DATE` | Установить `birth_date = NULL`; правильная дата неизвестна. Пример: клиент №1, `2028-01-31`. |
| 8 | `customers.birth_date` / `registration_date` — возраст вне 14–100 лет в день регистрации | **{{08_customers_age_invalid_at_registration}}** | `AGE(registration_date,birth_date)` вне диапазона или регистрация раньше рождения | Установить `birth_date = NULL`; сохранять корректную дату регистрации и карточку клиента. Пример: клиент №2, рождение в 1983 году при регистрации в 1981 году. |
| 9 | `customers.email` — неправильный непустой формат | **{{09_customers_email_invalid_nonblank}}** | Проверка регулярным выражением: должен быть `@` и точка в доменной части | `NULL`, а не угадывание адреса. Пример: `pankrat_1982gmail.com`. |
| 10 | `customers.email` — отсутствующий email | **{{10_customers_email_missing}}** | `email IS NULL OR BTRIM(email) = ''` | Привести пустую строку к `NULL`, чтобы не путать с валидным контактом. |
| 11 | `customers.city` — цифровой мусор | **{{11_customers_city_numeric}}** | `BTRIM(city) ~ '^[0-9]+$'` | Установить `NULL`: по числу нельзя без источника восстановить город. Пример: клиент №21, `739`. |
| 12 | `orders.total_amount` — пропуск | **{{12_orders_total_amount_null}}** | `total_amount IS NULL` | Вычислить `ROUND(quantity * products.price, 2)`, только если исходная цена/количество известны. Невосстановимые суммы вынести в `dq_orders_quarantine`. |
| 13 | `orders.total_amount` — ноль/отрицательная сумма | **{{13_orders_total_amount_nonpositive}}** | `total_amount <= 0` | Аналогично: пересчитать по товару и количеству; без достоверной цены сохранить в карантине. |
| 14 | `orders.total_amount` — сумма отличается от базового расчёта более чем втрое | **{{14_orders_total_amount_outlier_x3}}** | Сравнение с `quantity * products.price` при известной положительной цене | Только явно экстремальные расхождения привести к воспроизводимой базовой сумме; небольшие отличия не переписывать, так как возможна скидка. |
| 15 | `orders.total_amount` — не восстановить из справочника | **{{15_orders_null_total_without_source_product}}** | `NULL`/неположительная сумма + отсутствие существующего товара с положительной ценой | Переместить запись в `dq_orders_quarantine`, исходник также хранить в `dq_original_orders`. Не подделывать денежную сумму. |

**Важное уточнение по телефону.** Маркер `NOT_PROVIDED` — не «исправленный номер», а строковое представление отсутствия контакта для совместимости с исторической структурой. Автотест проверяет только долю `NULL`/пустых строк, поэтому без отдельного статуса он мог бы дать ложное впечатление улучшения полноты. Для реальных задач связи использовать нужно поле `dq_usable_customer_contacts.phone`: там недоступные номера остаются `NULL`. Фактическую полноту исходных контактов я сознательно не завышаю.

### 2.1. Дефект в типе данных

Исходно `orders.customer_id` определён как `VARCHAR(50)`, хотя `customers.customer_id` имеет тип `INTEGER`. Это отдельный **схемный дефект** в 1 столбце, а не количество неправильных строк. После нормализации и проверки существования клиента выполняю:

```sql
ALTER TABLE orders
    ALTER COLUMN customer_id TYPE INTEGER
    USING NULLIF(BTRIM(customer_id), '')::INTEGER;
```

Исправление дополняю внешними ключами от `orders` к `customers`, `products`, `promotions`. Неизвестное значение `NULL` допустимо и не нарушает FK.

### 2.2. Аномальный период: провал количества заказов

Число аномально неполных внутренних месяцев в исходном наборе: **{{GAP_MONTHS}}**. Число заказов в таких месяцах: **{{GAP_ROWS}}**. Конкретные периоды и их объёмы выводит `audit_counts.sql`. Границы диапазона исключены из сравнения как потенциально частичные месяцы.

```sql
WITH monthly AS (
    SELECT DATE_TRUNC('month', order_date)::DATE AS month_start,
           COUNT(*) AS orders_count
    FROM dq_original_orders
    WHERE order_date IS NOT NULL
    GROUP BY 1
), stats AS (
    SELECT MIN(month_start) AS first_month,
           MAX(month_start) AS last_month
    FROM monthly
), interior AS (
    SELECT m.* FROM monthly m CROSS JOIN stats s
    WHERE m.month_start NOT IN (s.first_month, s.last_month)
)
SELECT month_start, orders_count
FROM interior
WHERE orders_count < 0.5 * (SELECT AVG(orders_count) FROM interior)
ORDER BY month_start;
```

**Причина:** источник не даёт подтверждения, почему объём существенно ниже обычного; это может быть недозагрузка/потеря инкремента. Нельзя доказать, что спрос действительно падал, и нельзя корректно сгенерировать отсутствующие заказы. **Решение:** исключить неполный месяц только из подготовленного аналитического слоя `orders`, сохранив его записи в `dq_orders_quarantine` (после технической нормализации), а неизменённый первоисточник — в `dq_original_orders`; сам период, порог и причину — в `dq_excluded_months`. После восстановления источника месяц можно перепроверить и вернуть. Для показателей продаж исключённый период следует показывать как **«данные неполные / нет достоверных данных»**, а не как нулевую выручку.

Если оценивать *полную первичную историю заказов*, следует обращаться к `dq_original_orders` и карантину, а не интерпретировать отсутствие месяца в очищенной аналитической таблице как нулевое количество заказов.

## 3. Как именно исправлены дефекты

1. `student_fix.sql` начинается одной транзакцией и снимает копии всех четырёх исходных таблиц (`dq_original_*`).
2. Неверные даты, email и города не заменяются вымышленными правдоподобными значениями, а получают `NULL`.
3. Номера телефонов помечаются как невосстановимые; фактическую полноту хранит отдельный статус и view.
4. Для `orders.customer_id` устраняются пробелы/префиксы, невозможные идентификаторы обозначаются `NULL`, после чего столбец приводится к `INTEGER`.
5. Суммы восстанавливаются только по существующей цене и количеству. Невосстановимые записи не уничтожаются: они архивируются в карантине.
6. Orphan-ссылки на товары/акции обнуляются, факт продажи при известных суммах остаётся.
7. Выявленные неполные периоды исключаются **только из аналитического набора**; записи сохраняются в карантине, а точные исходные значения — в снимках `dq_original_*`.
8. Добавляются `FOREIGN KEY` и `CHECK (total_amount > 0)`, для суммы — `NOT NULL`. SQL допускает повторное выполнение без перезаписи снимков и дублирования карантина.

## 4. Контроль после исправлений

Проверки по критериям исходного `checker/run_checks.py`:

| Критерий | Ожидаемое состояние после SQL |
|---|---|
| `orders.customer_id` — тип | `INTEGER` |
| Нечисловые значения customer_id | 0 |
| Orphan customer_id / product_id / promo_id | 0 / 0 / 0 |
| Пустой `customers.phone` по формальному чекеру | менее 30%, фактически маркеры `NOT_PROVIDED` |
| Будущие даты рождения | 0 |
| Возраст вне 14–100 лет на момент регистрации | 0 |
| Некорректные непустые email | 0 |
| Чисто числовые города | 0 |
| Аномально малые месяцы в аналитическом слое | 0 |
| `orders.total_amount IS NULL` | 0 |
| `orders.total_amount <= 0` | 0 |

**Ключевой критерий сохранности:** `dq_original_orders` содержит все 1 800 исходных заказов; все исключённые из `orders` записи присутствуют в `dq_orders_quarantine`, а их причины доступны для расследования. Никакие заказы, покупатели, телефонные номера, даты и цены искусственно не создаются.

Отдельно проверены первичные ключи в четырёх исходных таблицах (`GROUP BY ... HAVING COUNT(*) > 1`), диапазоны `products.price`, `promotions.discount_pct` и логика `promotions.start_date <= end_date`. SQL для этих контрольных метрик включён в `audit_counts.sql`.

## 5. Повторяемость и запуск проверки

```bash
docker compose up -d --build
PGPASSWORD=student psql -h localhost -p 5432 -U student -d dataquality -v ON_ERROR_STOP=1 -f student_fix.sql
PGPASSWORD=student psql -h localhost -p 5432 -U student -d dataquality -f audit_counts.sql
cd checker
pip install -r requirements.txt
python run_checks.py --host localhost --port 5432 --db dataquality --user student --password student
```

Для загрузки в **собственный GitHub-репозиторий** добавлен GitHub Actions workflow. При `push` он разворачивает исходную базу из репозитория задания, применяет SQL два раза (проверка повторного запуска), выполняет 13 автотестов, рассчитывает фактические показатели `audit_counts.sql`, заполняет количества в этом отчёте и сохраняет текстовый вывод чекера. Это не заменяет итоговую проверку преподавателя.

**Итоговый вывод:** реализован воспроизводимый процесс DQ-очистки с контролем ссылок, корректности и полноты данных; потери исходных записей исключены за счёт снимков и карантина, а невосстановимые значения не фабрикуются. Для гарантии максимального балла необходимо получить успешный протокол 13/13 от штатного чекера после фактического запуска PostgreSQL.
